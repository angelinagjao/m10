1. What is R Shiny?

Shiny is an R package that allows you to build interactive web applications straight from R. It bridges the gap between complex data analysis and end-user accessibility.

  • No web dev skills needed: It builds the HTML, CSS, and Bootstrap framework for you behind the scenes.
  • Highly accessible: Users just need a web URL to interact with the dashboards.
  • Dynamic: It easily converts our standard static plots (like ggplot2) into interactive tools.

2. The Core Architecture of a Shiny App

Every Shiny app is built on two primary components that communicate with each other. You can store these as a single app.R file, or separate them into ui.R and server.R for larger team projects.

2.1. The User Interface (UI)

The UI is the front-end skeleton. It dictates what the user sees, how the page is laid out, and how they interact with the tool.

  • Layouts: You define the structural grid here. You can use standard setups like fluidPage with a sidebarLayout (which splits the screen into a sidebar for controls and a main panel for the graph), or you can use the shinydashboard package to build highly professional, modular dashboards with headers, sidebars, and body tabs.
  • Inputs: These are the widgets the user plays with to change the data. Examples include:
    • selectInput: A dropdown menu.
    • textInput: A text entry box.
    • sliderInput: A sliding numeric scale.
ImportantCrucial Rule

Every input must be assigned a unique ID (e.g., inputId = "post_type") so the Server knows exactly what to listen to.

  • Outputs: This is where you tell the UI to reserve visual space for the final product (e.g., plotOutput, tableOutput, textOutput).

2.2. The Server (The Brains)

The server works behind the scenes to take the inputs, process the data, and generate the outputs.

  • The server is initialized as a function with three arguments: input, output, and session.
  • Input is Read-Only: The server can only listen to the user’s input; it cannot change it. To interact with an input you defined in the UI, you call it using input$your_id (e.g., input$post_type).
  • Rendering Outputs: When you generate a graph or table, it must be wrapped in a specific reactive context to be sent back to the UI, such as renderPlot for a ggplot or renderText for a dynamic title.

3. The Magic of Reactivity

This is the most important concept to grasp. Shiny is built on declarative programming rather than standard imperative programming.

In a standard R script, order strictly matters. You tell the computer exactly what to do line-by-line. In Shiny, you teach the app how to react if and when an input changes.

  • Reactive Dependencies: If an output depends on a specific input, Shiny creates a “reactive dependency.” Whenever the user moves a slider, Shiny automatically knows to trace that input back, recalculate the specific block of code tied to it, and instantly update the visual output.
  • Reactive Expressions reactive({}): If you are filtering a large dataset before plotting it, you don’t want to rewrite the filtering code for every single plot. You can create a reactive expression that filters your dataset based on the user’s input, saves it as an intermediate reactive object, and then passes that clean data to your output elements.
Note

When calling a reactive dataframe in the server, you must use parentheses, e.g., filtered_data().

4. Best Practices for Workflow

When we are building out these tools for the team, we should follow a structured sequence:

  1. Sketch it out: Before coding, literally draw the dashboard on a piece of paper. Decide where the inputs go and what the final visual should look like.
  2. Load Data Outside Reactivity: Read in your main CSV files or establish your basic tidy data at the very top of the script (or in the global environment) so the app only has to load the heavy data once upon startup, rather than every time the user clicks a button.
  3. Build the static visual first: Write your ggplot or data wrangling code normally. Ensure the logic works first, then simply replace your hardcoded filter variables with the Shiny input$... variables.

5. Deployment and Security

Once the app is built, it isn’t useful if it only lives locally on our IDEs.

  • Deployment: You can bundle the app and host it on the cloud using services like shinyapps.io or Posit Cloud. By clicking the “Publish” button, R packages up the environment and deploys it to a live web URL.
  • Security: If the dashboard contains sensitive operational metrics, you cannot leave the URL open to the public. For basic projects, the shinymanager package allows you to easily wrap your UI in a secure login screen, requiring a simple username and password to access the data.
